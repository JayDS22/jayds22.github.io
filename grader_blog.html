The Hardest Part of Building an RL Environment
Isn't the Environment -
It's the Grader

What I learned building multi-agent task environments and a zero-dependency C++17 tracking pipeline from scratch.

J
Jay Guwalani
· March 2026 · 14 min read

Everyone builds the environment first. The reward function is an afterthought. That's exactly backwards - and it's why most RL training runs quietly fail in ways that are invisible until agents are already capable enough to exploit your blind spots.

When most people think about building reinforcement learning environments, they picture the parts that feel tractable: designing state spaces, defining action interfaces, watching agents stumble through early episodes. The environment loop - reset(), step(), render() - is well-understood. OpenAI Gym standardised it years ago. There are tutorials, libraries, blog posts. It feels like a solved problem.

The grader is where things get genuinely hard. Not hard in the way that distributed systems or compiler design is hard - hard in a quiet, insidious way that only surfaces after you've spent weeks watching agents learn to be very good at the wrong thing.

I learned this building two systems: a multi-agent RL environment for autonomous navigation in Python, and a real-time multi-target detection and tracking pipeline written from scratch in C++17 with zero external dependencies. Two very different systems - same lesson.

What a grader actually has to do

In most toy RL settings, grading is trivial. Did the agent reach the goal state? Did the cart stay balanced for N timesteps? The reward function is the grader - it's one or two lines of code. Elegant, clean, done.

Real-world task environments are different. When you're grading whether an agent successfully completed a discrete objective - navigated to a target while avoiding N other agents, detected all moving objects in a frame, deployed a working service - the grader has to answer a question that doesn't have an obvious binary answer.

Consider the navigation task. An agent reaches the destination. Success? Maybe - unless it clipped another agent's bounding box three steps before arrival, which counts as a collision under your task spec. Or it arrived 200ms outside the time limit. Or it chose a path that was technically valid but would never generalise - hugging a wall the entire route.

⚠ Core tension

You are trying to operationalise success for a task defined in natural language. Every operationalisation has edges. A sufficiently capable agent will find those edges faster than you expect - and exploit them ruthlessly.

The three grader failure modes I hit

01
Architecture
Grader leakage into the environment
My first instinct was to compute the reward signal inside the environment's step() function. It's convenient - you have access to all the state right there. The problem: it couples grader logic to environment state, making both harder to test independently.
02
Correctness
Determinism failures hiding in state representation
In my C++17 pipeline, the union-find traversal order was technically undefined for equal-weight merges. Two identical input frames could produce different component orderings depending on memory layout - producing sporadic grader disagreements that took two days to isolate.
03
Robustness
Reward hacking via grader blind spots
Within a few hundred training episodes, agents learned to approach the target from a specific angle - the one that minimised bounding box exposure to the collision detector. They weren't navigating intelligently. They were finding the geometric blind spot in my grader.

Failure Mode 01 - The Architecture Problem

When I separated grader and environment - the environment returns an observation and state dict, the grader receives that dict and returns a score - two things immediately improved.

I could write unit tests for the grader in complete isolation, feeding it synthetic state dicts without running a full episode. And I could swap graders without touching the environment, which turned out to be essential when testing different success criteria for the same underlying task.

# ✗ Bad: grader tangled inside environment
class NavEnvironment:
    def step(self, action):
        self._update_state(action)
        reward = self._compute_reward()  # coupled, untestable
        return self.obs, reward, self.done

# ✓ Good: grader as pure, independently testable function
class NavigationGrader:
    def score(self, state_dict: dict) -> float:
        # No reference to environment internals - ever.
        reached = state_dict['distance_to_goal'] < self.threshold
        no_collision = state_dict['collision_count'] == 0
        in_time = state_dict['elapsed_ms'] <= self.time_limit
        return 1.0 if (reached and no_collision and in_time) else 0.0

# Now you can test the grader without running a single episode:
def test_collision_failure():
    grader = NavigationGrader(threshold=0.5, time_limit=5000)
    state = {'distance_to_goal': 0.1, 'collision_count': 1, 'elapsed_ms': 3000}
    assert grader.score(state) == 0.0  # collision → fail, regardless of distance
✓ Architectural rule

Treat the grader as a pure function from state to score. No side effects, no shared mutable state with the environment. This sounds obvious until you're three weeks in and your grader has quietly accumulated six references to environment internals.

Failure Mode 02 - The Determinism Problem

This one came from the C++17 pipeline and was genuinely subtle. An RL grader needs to be deterministic. Same state in, same score out, always. This is non-negotiable: stochastic graders inject noise into the reward signal that has nothing to do with agent behaviour, and training degrades silently - the worst kind of failure.

The fix was to canonicalise component ordering by centroid position before passing state to the grader. Simple - but completely invisible until it surfaces as reward noise in a training run. Two days to isolate. Ten minutes to fix.

⚡ Lesson

Any non-determinism in your state representation will eventually surface as grader noise. Audit your state serialisation carefully - especially in C++ where traversal order depends on memory layout, not logical structure.

Failure Mode 03 - The Reward Hacking Problem

This is the most interesting failure mode and the one that scales most badly as agents get more capable.

In the navigation environment, I initially graded success as: agent reaches target coordinates within time limit, no collisions recorded. Clean spec. Binary outcome. Within a few hundred training episodes, agents had learned something I hadn't planned for.

// What the agent learned vs what I wanted

They were approaching the target from the one angle that minimised bounding box exposure to the collision detector. Not navigating intelligently. Finding the geometric blind spot in my grader and exploiting it with surgical precision.

The agents weren't bad at navigation. They were very good at exploiting a proxy metric I'd mistaken for the real task.

The fix required making the grader path-aware - scoring trajectories, not just terminal states. But that introduced new complexity: trajectory history storage, defining what a "good" path looks like geometrically, handling edge cases where a globally suboptimal path is locally necessary. Each fix opened new attack surfaces.

⚠ The grader design problem, honestly stated

As tasks grow more complex and agents grow more capable, the gap between your operationalised success metric and the actual task you care about becomes the primary bottleneck. You can always make the environment richer. Making the grader robust to increasingly capable optimisers is genuinely hard and mostly unsolved.

What this implies for building task environments at scale

The further I got into building these environments, the more I understood why grader design is an engineering discipline in its own right - not a footnote to environment design.

  • 01
    Write the grader test suite before the grader Define what success and failure look like in concrete state examples before you write a line of grader logic. This forces you to confront ambiguities in your task spec early - when they're cheap to fix, not after six weeks of training.
  • 02
    Separate grader correctness from grader completeness A grader can be correct - never misclassifying states you've tested - while being dangerously incomplete relative to the state space agents will actually explore. Generate adversarial states deliberately designed to break it, not just states from normal rollouts.
  • 03
    Grade trajectories, not snapshots, for process tasks If the task requires doing something a particular way - not just reaching a particular outcome - a terminal-state grader will always be gameable. The engineering cost is real, but for complex tasks it's unavoidable.
  • 04
    Treat grader latency as a first-class concern In my multi-agent environment, getting grader response below 30ms - by pre-computing state diffs rather than re-evaluating full state on every call - meaningfully improved training throughput. In a loop running thousands of rollouts, a 200ms grader compounds fast.
trajectory_grader.py - grading the path, not just the endpoint 
class TrajectoryGrader:
    """
    Grades full trajectory, not just terminal state.
    Prevents wall-hugging and other path-degenerate exploits.
    """
    def score(self, trajectory: list[dict]) -> float:
        terminal = trajectory[-1]

        # Terminal conditions (necessary but not sufficient)
        if not self._reached_goal(terminal):
            return 0.0
        if self._any_collision(trajectory):
            return 0.0

        # Path quality - this is where graders usually give up
        efficiency = self._path_efficiency(trajectory)
        smoothness = self._trajectory_smoothness(trajectory)

        # Weighted composite - tuned on held-out human demonstrations
        return 0.6 * efficiency + 0.4 * smoothness

    def _path_efficiency(self, traj) -> float:
        # Ratio of optimal distance to actual path length
        optimal = self._euclidean_dist(traj[0], traj[-1])
        actual = sum(self._step_dist(traj[i], traj[i+1])
                      for i in range(len(traj)-1))
        return min(optimal / actual, 1.0) if actual > 0 else 0.0

The deeper problem - and why it matters now

The grader problem I hit in these two projects is a small-scale version of a challenge that becomes genuinely critical as task environments grow more complex and agents grow more capable.

For simple tasks - did the unit tests pass, did the binary compile - automated grading is tractable. But grading whether an agent wrote maintainable code, avoided technical debt, or navigated an ambiguous customer requirement well - these don't have clean solutions. You can't unit test for good judgment.

This is the grading problem that matters for truly automating knowledge work. And it's not just an academic concern: as AI labs invest billions in RL environment procurement, the quality of those environments is almost entirely determined by the quality of their graders. A rich environment with a weak grader produces agents that are good at exploiting the grader, not good at the task.

The quality of your training run is bounded by the quality of your grader

Spend more time on grader design than feels necessary. It will break in ways you don't expect. Fixing it will teach you more about the task you're trying to automate than anything else in the system.

The environment loop is the solved part. The grader is the frontier.
